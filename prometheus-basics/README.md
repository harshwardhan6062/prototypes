# prometheus-basics

A metrics endpoint written by hand, with no Prometheus client library, so the
whole thing fits in one readable file.

The point: **a Prometheus exporter is not a protocol or a client. It is one HTTP
endpoint that returns plain text.** Prometheus GETs that text every few seconds
and stores the numbers. That is the entire system.

## Run

```bash
python3 app.py          # stdlib only, no pip install

docker run -d --name prom-basics -p 9095:9090 \
  --add-host=host.docker.internal:host-gateway \
  -v "$PWD/prometheus.yml:/etc/prometheus/prometheus.yml:ro" \
  prom/prometheus:v2.54.1

open http://localhost:9095            # Prometheus UI
curl localhost:8000/metrics           # the raw text it scrapes
```

## What the app exposes

```
# HELP app_requests_total Requests handled, by path and status.
# TYPE app_requests_total counter
app_requests_total{path="/work",status="200"} 4
# TYPE app_in_flight_requests gauge
app_in_flight_requests 0
# TYPE app_request_duration_seconds histogram
app_request_duration_seconds_bucket{le="0.005"} 2
app_request_duration_seconds_bucket{le="0.01"} 4
...
app_request_duration_seconds_bucket{le="+Inf"} 4
app_request_duration_seconds_sum 0.018
app_request_duration_seconds_count 4
```

One line per series. `name{labels} value`. Nothing else.

## The three metric types, and why they differ

| Type | Behaviour | You query it with |
| --- | --- | --- |
| **Counter** | Only goes up. Resets to 0 on restart | `rate()` — never the raw value |
| **Gauge** | Goes up and down. A snapshot of *now* | the value directly |
| **Histogram** | Latency, in cumulative buckets | `histogram_quantile()` |

**Counters are the one people misuse.** `app_requests_total` is 48,213 — that
number is meaningless on its own. What you want is `rate(...[1m])`, which is
also what makes a process restart harmless: `rate()` detects the reset and
handles it.

**Histograms are the one worth reading the code for.** The buckets are
*cumulative* — a request taking 8ms increments `le="0.01"`, `le="0.025"`,
`le="0.05"` and every larger bucket. Then `_sum` and `_count` are published
alongside. `histogram_quantile()` interpolates a percentile from those counts,
which is why the answer is approximate and why bucket choice matters.

## Queries to try

```promql
sum by (status) (rate(app_requests_total[1m]))                       # req/sec
histogram_quantile(0.95, sum by (le) (rate(app_request_duration_seconds_bucket[1m])))
rate(app_request_duration_seconds_sum[1m])
  / rate(app_request_duration_seconds_count[1m])                     # mean latency
sum(rate(app_requests_total{status="500"}[1m]))
  / sum(rate(app_requests_total[1m]))                                # error ratio
```

Measured on a run where the code injects 10% errors and a 0.4s slow path:

```
requests/sec   200: 1.375    500: 0.167
p95 latency    0.4454        <- lands on the slow path, as designed
mean latency   0.1124
error ratio    0.1084        <- matches the 10% in the code
```

## Break it on purpose

**Kill the app** while Prometheus is running. The target goes `down` in the UI
within seconds, and `up{job="hand-written-app"}` becomes 0 — that series is
generated by Prometheus itself, not by you, which is why it is the standard
thing to alert on.

**Restart the app.** Every counter resets to 0. Graph the raw counter and you
get a cliff; graph `rate()` and the line is unbroken. That difference is the
whole argument for counters over gauges.

**Scrape it yourself** — `curl localhost:8000/metrics` is byte-for-byte what
Prometheus receives. There is nothing else to the wire format.

## Notes

- `/metrics` deliberately does not count or time itself. Scrapes are not user
  traffic, and including them skews every graph.
- Prometheus **pulls**. The app has no idea Prometheus exists, holds no
  connection to it, and needs no config pointing at it.
- The app generates a little load on itself so the graphs are not flat.
